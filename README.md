# Attractions Local - Standalone Spring Boot Maven Application

A Windows-friendly version of the attractions architecture. It requires **no Docker, Kafka, Redis, PostgreSQL, or external supplier credentials**.

## Architecture

```text
Browser
   |
   v
Spring Boot REST API + Frontend
   |
   +--> H2 file database
   |
   +--> Caffeine local cache
   |
   +--> Scheduler (rolling 90-day refresh)
   |       |
   |       +--> Async supplier worker pool
   |                |
   |                +--> Supplier A simulator
   |                +--> Supplier B simulator
   |                +--> Supplier C simulator
   |
   +--> Price aggregation -> minimum available price per product
```

The local version intentionally replaces infrastructure that normally needs Docker/AWS:

| Production design | Local standalone equivalent |
|---|---|
| PostgreSQL/RDS | H2 file database |
| Redis/ElastiCache | Caffeine in-process cache |
| Kafka/MSK | Spring async events / task executor |
| Real supplier APIs | `SupplierSimulator` |
| ECS/EKS | One executable Spring Boot application |

The domain separation remains the same: the Product Catalog owns static attraction information and supplier mappings; the availability process owns dynamic availability/pricing; the query API serves the cheapest results.

## Requirements

- Windows 10/11
- JDK 21
- Maven 3.9+

Check:

```bat
java -version
mvn -version
```

## Run in Eclipse

1. Extract the ZIP.
2. Eclipse -> **File -> Import -> Existing Maven Projects**.
3. Select the extracted `attractions-local` folder.
4. Wait for Maven dependencies to download.
5. Run `AttractionsApplication.java` as **Spring Boot App**.
6. Open http://localhost:8080/

Or from Command Prompt:

```bat
mvn clean spring-boot:run
```

Or build a standalone executable JAR:

```bat
mvn clean package
java -jar target/attractions-local-1.0.0.jar
```

## Frontend

Open:

http://localhost:8080/

Choose London or New York and click **Find cheapest attractions**.

The application returns up to 20 products ordered by the minimum available price found at any time/date in the next 90 days.

## H2 Console

Open:

http://localhost:8080/h2-console

Use:

```text
JDBC URL: jdbc:h2:file:./data/attractions
User:     sa
Password: [blank]
```

The database is persisted under the application's `data` directory.

## Database scripts / demo data

`src/main/resources/db/data.sql` automatically loads 12 London attractions and 12 New York attractions, plus supplier mappings.

There are also copies/reference scripts under `scripts/`:

- `01-create-database.sql` - H2 setup notes
- `02-demo-data.sql` - London/New York catalogue and supplier mappings
- `03-reset-database.bat` - deletes the local H2 files so the application can recreate the demo database

The availability records are deliberately generated by the application rather than hard-coded for 90 days. This demonstrates the real ingestion flow: product mappings -> scheduled supplier requests -> availability -> price aggregation -> cache -> query API.

## API examples

Get London:

```text
GET http://localhost:8080/api/v1/cities/London/attractions/cheapest?limit=20
```

Get New York:

```text
GET http://localhost:8080/api/v1/cities/New%20York/attractions/cheapest?limit=20
```

Trigger an asynchronous refresh:

```text
POST http://localhost:8080/api/v1/admin/refresh
```

Clear local cache:

```text
POST http://localhost:8080/api/v1/admin/cache/clear
```

View catalogue:

```text
GET http://localhost:8080/api/v1/catalog/products?city=London
```

Health:

http://localhost:8080/actuator/health

## Important implementation detail

The scheduled refresh maintains the rolling 90-day window. The demo supplier returns deterministic prices based on product/date so repeated runs are reproducible while still looking like real supplier responses.

For an AWS deployment, the next step would be to replace the local adapters with RDS, ElastiCache, Kafka/MSK, real supplier WebClient clients, Secrets Manager and ECS/EKS without changing the core API/domain model.
